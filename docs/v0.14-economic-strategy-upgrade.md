# Arena Hero v0.14 Economic Strategy Upgrade

## Status

This document records the approved requirements and the implemented v0.14
production policy. The strategy remains deterministic and keeps the existing
12-Worker baseline while enabling measured growth in the default profile.
The implementation is validated locally; controlled production deployment is a
separate operational step and has not been performed by this change.

The local Windows deployment has already completed the protocol-compatibility
layer:

- Official Python SDK is pinned and installed at `arena-hero==0.2.9`.
- The reviewed contract baseline is API `v0.1`, gameplay `v0.14`, and SDK
  `0.2.9`.
- The SDK upgrade removed `PlayerState.population_tier` and
  `PlayerState.upkeep_next_tick`; the test fixture was updated accordingly.
- The complete offline suite passes after the compatibility update.

## Upstream Rule Change

Gameplay v0.14 replaces maintenance with exact population-based Unit prices:

- Population 1 through 20: base prices apply: Worker `5`, Vanguard `10`, and
  Ranger `12`.
- Population 21 through 25: each Unit price is multiplied by `1.3`.
- Above population 25: the multiplier gains another `1.3` factor for every
  additional five living Units.
- The server calculates the actual price after combat using the population that
  survives that Tick.
- The official SDK exposes `unit_cost(unit_type, population)` for this rule.

The implemented strategy keeps `12 Worker + 3 Vanguard + 4 Ranger = 19` as
its baseline, grows toward `17 Worker + 3 Vanguard + 4 Ranger = 24` only after
a self-funding deposit window, and reserves population 25 for one emergency
defender. Population 25 is an absolute policy bound. The previous explanation
that 20 population causes a resource penalty is obsolete.

## Implemented Policy

- The default profile grows one Worker at a time from population 19 toward 24.
- Growth requires 32 complete Ticks of successful deposits with no recorded
  return or resource-route blocking, and deposits totaling at least twice the
  next Worker price.
- Optional growth retains `10 + unit_cost(RANGER, population + 1)` resources
  after accounting for already planned Unit healing.
- Immediate threats can add one emergency Vanguard or Ranger up to population
  25 after safe Core evasion is unavailable.
- All production prices use `unit_cost()` with `turn.state.population`.
- At a dynamic price boundary, an immediate defender replacement may use a
  conditional post-combat quote only when a no-loss resolution would be
  unaffordable; failed conditional attempts enter a bounded backoff.
- Failed or queued spawns do not update local economic state until a matching
  event and the new Unit in authoritative state confirm the result.

## Objective

Replace the fixed 19-population economic policy with a version-aware,
risk-aware production policy that can profitably exceed population 20 while
avoiding uneconomic high-price Unit production.

The implementation must preserve the current safety properties: deterministic
planning, bounded fleet size, Core survival priority, no concurrent control of
the same game state, and conservative behavior during protocol uncertainty.

## In Scope

1. Replace production affordability checks based on static constants with the
   official `unit_cost()` calculation using the authoritative current
   population.
2. Recalculate Worker expansion, defensive reserve, recovery, emergency spawn,
   and post-combat replacement thresholds using the next Unit's dynamic cost.
3. Introduce an explicit population-growth policy that decides when to:
   - remain at or below population 20;
   - add Workers for resource throughput;
   - add combat Units for a measured threat or opportunity;
   - stop expansion because the next price tier is not economically justified.
4. Make the policy account for the resolution order: combat changes population
   before the server charges for a Core spawn in the same Tick.
5. Keep safe Core reserve and healing decisions ahead of optional production.
6. Add deterministic tests for each price boundary: population 19/20, 20/21,
   25/26, and at least one later tier.
7. Add scenario tests covering normal expansion, combat losses followed by a
   same-Tick replacement opportunity, low-resource recovery, and sustained
   threat.
8. Update user-facing strategy and compatibility documentation after behavior
   is implemented and validated.

## Explicit Non-Goals

- Do not blindly raise every population target or remove all fleet bounds.
- Do not change threat, movement, scouting, Ranger geometry, or Core migration
  logic unless a test demonstrates that the economic policy requires it.
- Do not add model-driven production control. The main Agent remains
  deterministic.
- Do not expose API keys, player identifiers, private logs, or plan contents in
  tests, diagnostics, or documentation.
- Do not enable the root-level optimizer as part of this task.

## Implementation Notes

The production policy is implemented in `arena_farmer.py` and covered by
`test_arena_farmer.py`:

- The official SDK `unit_cost()` is used for Worker, Vanguard, Ranger,
  recovery, reserve, and staged expansion comparisons.
- `turn.state.population` is used for quotes, resource-ledger population, and
  liveness diagnostics.
- Optional growth is isolated from tactical movement through a deterministic
  32-Tick deposit window and explicit population constants.
- The test fixture supports an independent authoritative population so price
  boundaries and protocol mismatches are testable.

## Design Constraints

- Use `arena_hero.unit_cost()` rather than duplicating the price formula in the
  Agent.
- Treat `turn.state.population` as authoritative for the planned spawn price.
- Do not assume a queued spawn succeeds; consume server resolution events and
  observed state before drawing economic conclusions.
- Keep integer comparisons exact. Do not use floating-point price tiers.
- Give optional expansion a lower priority than Core repair/healing, immediate
  evasion, and required defense.
- Bound any new maximum population through a named, documented policy constant
  or configuration option with a safe default.
- Retain current defaults unless tests and measured behavior justify changing
  them.

## Acceptance Criteria

The upgrade is complete only when all of the following are true:

1. No production decision relies on a hard-coded Unit price where the current
   population can be 20 or greater.
2. The Agent uses the official SDK price helper for all new affordability and
   reserve decisions.
3. Tests prove expected behavior at every specified dynamic-price boundary.
4. Tests prove Core-safety behavior remains dominant when dynamic pricing would
   otherwise permit a spawn.
5. The full offline test suite, compilation check, dependency check, and secret
   scan pass.
6. Documentation reflects v0.14 accurately and no longer presents the legacy
   maintenance model or a 20-population resource penalty as active behavior.
7. The deployed process is restarted deliberately after verification; logs show
   no protocol mismatch, authentication failure, or repeated rejected plans.

## Implementation Sequence

1. Stop the active Agent before changing strategy code so a half-updated
   editable installation cannot influence play.
2. Read the current upstream contract page and verify the SDK version remains
   `0.2.9` before beginning.
3. Add failing price-boundary and production-priority tests.
4. Refactor pricing and reserve calculations around `unit_cost()`.
5. Define and test the growth policy separately from tactical movement.
6. Update strategy, configuration, and README documentation to match the new
   policy.
7. Run the full validation suite, review the diff, then restart and monitor one
   controlled deployment.
